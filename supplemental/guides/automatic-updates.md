# Automatic update monitoring

Beszel can collect a read-only snapshot of Debian and Ubuntu automatic update health. The feature monitors `unattended-upgrades`; it never installs packages, refreshes APT metadata, changes APT or systemd configuration, runs an upgrade, or reboots the machine. Connectivity is unchanged: `HUB_URL` continues to accept any URL the Agent can reach.

## Agent configuration

The feature is opt-in in the Agent binary. The Linux installation command generated by this fork enables it with:

```ini
UPDATE_MONITORING=true
UPDATE_CHECK_INTERVAL=6h
UPDATE_CHECK_TIMEOUT=30s
UPDATE_MAX_PACKAGE_LIST=50
```

Set `UPDATE_MONITORING=false` (or remove it) and restart the Agent to disable all update-related commands and log access. The interval must be at least one minute, the timeout between one second and five minutes, and the package limit between 0 and 500.

The installer adds the `beszel` user to the existing `adm` and `systemd-journal` groups on Debian/Ubuntu on a best-effort basis. These memberships allow the unprivileged Agent to read the usual APT and journal data; installation does not fail if either group is absent. The Agent does not need to run as root.

## Data sources and collection

- `/etc/os-release` identifies Debian and Ubuntu. Other platforms report `unsupported` and continue normal monitoring.
- `dpkg-query` is authoritative for package installation. `/usr/bin/unattended-upgrade` is only a limited fallback when `dpkg-query` itself is unavailable.
- `apt-config dump` supplies the effective `APT::Periodic` values, including overrides from later configuration files.
- The existing systemd D-Bus connection reads the APT timers and services. A completed inactive oneshot service is not treated as a failure.
- Ubuntu's `apt-check` supplies total and security counts. A read-only `apt-get -s -o Debug::NoLocking=true upgrade` is the fallback; its security count remains unknown rather than becoming zero.
- `/run/reboot-required` and `/run/reboot-required.pkgs` supply reboot state.
- A bounded tail (256 KiB) of the current or once-rotated APT history supplies the latest timestamp and at most the configured package count. Missing or unreadable logs result in partial data, not an Agent failure.

Expensive work runs in a background goroutine with the configured timeout. The normal metrics request only copies an in-memory snapshot. A failed refresh preserves the previous snapshot and increases `cache_age_seconds`; no APT command runs when monitoring is disabled. At the default six-hour interval this is a small burst of process and disk activity four times per day. This is suitable for constrained systems such as Raspberry Pi Zero 2 W; increasing the interval further reduces wakeups.

## States

Overall-state precedence is: `unsupported`, `not_installed`, `installed_not_configured`, `configured_disabled`, `last_run_failed`, `update_in_progress`, `reboot_required`, `updates_pending`, `monitoring_incomplete`, `healthy`, then `unknown`. This makes failures and active maintenance visible before lower-priority pending work.

- `healthy`: package and effective configuration are enabled and timers are active.
- `updates_pending`: one or more cached updates are available.
- `reboot_required`: the operating system created the reboot marker.
- `last_run_failed`: systemd reports that the last automatic upgrade failed.
- `update_in_progress`: the automatic upgrade service is active.
- `monitoring_incomplete`: one or more required data sources are unavailable or the cache is not ready.
- `not_installed`, `installed_not_configured`, and `configured_disabled`: distinguish package, configuration, and enablement problems.
- `unsupported`: any operating system other than Debian or Ubuntu, including non-Linux Agents.

The Hub stores the current snapshot in the system record, separately from CPU/RAM/disk time series. Relevant transitions are written to the existing history as `maintenance:*` events, so identical minute samples do not create duplicates.

## Alerts and limitations

The alert editor includes package missing, automatic updates disabled, last update failed, security updates pending, reboot required, and stale information. Unknown values do not trigger alerts, and normal alert resolution/history and quiet-hours behavior is retained.

The first version depends on the host's existing APT cache and accessible systemd/log metadata. It does not call `apt update`, so pending counts can only be as current as that cache. Security counts may be unknown outside Ubuntu or when `apt-check` is unavailable. Localized free-form log error messages are not used to infer failure; systemd's structured result is preferred.
